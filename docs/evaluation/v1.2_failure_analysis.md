## 1. Executive Summary

This report delivers a rigorous, evidence-driven failure analysis of the completed Knowledge Intelligence Platform (KIP) v1.2 expanded retrieval baseline.

The v1.2 expanded baseline evaluated **80 labelled benchmark cases** across **6 categories** against an expanded corpus of **50 documents** (38 core KIP architectural documents + 12 adversarial distractors) indexed in Qdrant Cloud using Google Gemini embeddings (`gemini-embedding-2`, 768 dimensions). The baseline completed with **0 infrastructure errors**, achieving an overall **Hit Rate @ 1 of 0.6875**, **Hit Rate @ 3 of 0.8375**, **Hit Rate @ 5 of 0.8750**, and a **Mean Reciprocal Rank (MRR) of 0.7623**.

### Key Findings

1. **Complete Retrieval Misses (10/80 cases, 12.5%):**  
   Ten queries returned zero relevant target documents in their top-5 results. The dominant failure mechanism is **Hard Negative Confusion** (6 of 10 misses), where distractor documents explicitly mentioning queried technologies (e.g., Redis caching, Conversational memory, Neo4j, LangGraph, WebSocket streaming) outranked the genuine KIP documents. Two misses stem from evaluation ground-truth incompleteness or terminology mismatches (`exp-007`, `exp-077`), one from cross-document dispersion (`exp-070`), and one from paraphrase distractor capture (`exp-026`).

2. **Ranking Imperfections (15/80 cases, 18.75%):**  
   Fifteen queries successfully retrieved the target document within the top 5, but failed to rank it at position 1. Of these, 5 represent hard negative distractors occupying rank 1 or 2, while at least 4 represent **Evaluation Ground-Truth Incompleteness** where an unlisted but factually accurate document (e.g., `kip_configuration_settings.txt` or `kip_api_specifications.txt`) legitimately outranked the single annotated target.

3. **Zero Chunk-Boundary Failures:**  
   Empirical verification revealed that all 50 documents in `corpus_v1_2_expanded` contain between 717 and 893 characters. Because the pipeline configured a fixed chunk size of 1,000 characters (200 overlap), **every document produced exactly one chunk (chunk index 0)**. Consequently, no relevant information was split across chunk boundaries; failures in the "boundary handling" category were caused by subtle semantic mismatches and multi-document overlap, not chunk boundary truncation.

4. **Latency Tail and Outlier Diagnosis:**  
   The baseline median latency is **538 ms** with a P90 of **613 ms** and P95 of **643 ms**. The overall mean of **1,261.02 ms** is heavily skewed by a single extreme outlier: `exp-018` at **55,050 ms** (~55 seconds), followed by `exp-020` at **2,930 ms**. Inspection of the codebase reveals that `EvaluationRunner` records a monolithic wall-clock measurement enclosing the HTTPS call to Gemini's embedding API and the Qdrant Cloud search. The 55s spike in `exp-018` is consistent with an upstream Gemini API rate-limit/throttling event where the `google-genai` SDK's internal exponential backoff retried before succeeding. Excluding `exp-018`, the mean retrieval latency is **579.5 ms**.

5. **Primary Recommended Next Experiment:**  
   **Two-Stage Retrieve-and-Rerank with a Cross-Encoder.** Retrieve top-20 candidates using the existing dense Gemini/Qdrant pipeline, followed by a cross-encoder reranker scoring the top-20 to produce the final top-5. This directly addresses the primary failure mode (hard negative confusion and rank inversion) while maintaining the 50-document corpus and 80-case benchmark.

### Category Performance Analysis

- **Multi-Concept (16/16 perfect, MRR 1.000):**  
  Queries combining multiple distinct architectural concepts (e.g., Qdrant + payload filters, Gemini + 768 dimensions) create rich, specific query vectors that pinpoint the target document without interference.

- **Paraphrase (15/16 perfect, MRR 0.9375):**  
  Gemini embeddings demonstrate high semantic invariance across natural paraphrasing. The sole failure (`exp-026`) was captured by an adversarial distractor.

- **Exact Terminology (11/16 H@1, MRR 0.7937):**  
  While 15 of 16 cases achieved Hit@5, four cases suffered rank degradation because the corpus contains multiple documents discussing the same technical facts (e.g., collection name, endpoint path, embedding dimensions).

- **Cross-Document (5/8 H@1, MRR 0.7500):**  
  7 of 8 cases achieved Hit@5. However, evaluation audit revealed that runner logic checks if *any* expected document is retrieved, masking cases where only 1 of 2 required documents was returned.

- **Boundary Handling (3/8 H@1, MRR 0.5250):**  
  Suffered significant rank degradation (4 ranking errors, 1 miss). Queries addressing system boundaries (rate limits, exception sanitization, missing workspace IDs) retrieved overlapping architectural security and error documents.

- **Hard Negative (5/16 H@1, MRR 0.4427):**  
  The primary vulnerability of the pure dense baseline. 6 of 16 cases completely missed the top 5, and 4 others were displaced from rank 1. Dense bi-encoders independently maximize semantic proximity to the distractor documents specifically crafted around the queried terms.

## 6. Latency Investigation

### Timing Instrumentation Architecture

Inspection of [`evaluation/runner.py`](file:///c:/Users/arun/OneDrive/Desktop/knowledge-intelligence-platform/evaluation/runner.py#L120-L145) establishes exactly what `retrieval_latency_ms` measures:

```python
t_ret_start = time.perf_counter()
# ...
chunks = self._retrieval_service.search(retrieval_query)
# ...
t_ret_end = time.perf_counter()
retrieval_latency_ms = (t_ret_end - t_ret_start) * 1000
```

Inside [`RetrievalService.search`](file:///c:/Users/arun/OneDrive/Desktop/knowledge-intelligence-platform/backend/app/services/retrieval/service.py#L35-L99):
1. Formats query and calls `EmbeddingService.embed_texts()`, which executes an HTTPS POST to Google's Gemini API via `google.genai.Client.models.embed_content()`.
2. Receives 768-dimensional float vector.
3. Calls `VectorStoreService.search()`, which executes an HTTPS REST/gRPC vector similarity query with payload filter against Qdrant Cloud.
4. Unpacks and filters `RetrievedChunk` domain models.

**Key Instrumentation Fact:** `retrieval_latency_ms` is a **monolithic wall-clock timer** encompassing network I/O to Google APIs, network I/O to Qdrant Cloud, and client-side serialization. There is **no sub-component breakdown** between embedding latency and vector search latency.

### Latency Distribution Statistics

From the 80 observations in `benchmarks/kip_v1_2_expanded_baseline_20261014_112147.json`:

- **Sample Size ($N$):** 80
- **Minimum:** 500 ms (`exp-076`, `exp-077`)
- **25th Percentile (Q1):** 524 ms
- **Median (50th Percentile):** 538 ms
- **75th Percentile (Q3):** 563 ms
- **Mean:** 1,261.02 ms
- **90th Percentile (P90):** 613 ms (case `exp-007`)
- **95th Percentile (P95):** 643 ms (case `exp-004`)
- **Maximum:** 55,050 ms (`exp-018`)

```
Latency Quantiles (ms):
Min: 500ms |----------- Median: 538ms --- P90: 613ms - P95: 643ms ------------------| Max: 55,050ms (Outlier)
```

### Outlier Investigation

Two cases exhibited latencies exceeding 2,000 ms:
1. **`exp-018`:** **55,050 ms** (~55.05 seconds)
2. **`exp-020`:** **2,930 ms** (~2.93 seconds)

#### Evidence-Based Diagnosis of `exp-018`
- **What is Established:**
  - Case `exp-018` is the 18th case executed in sequential order.
  - The query text is standard length (78 characters): *"By what specific method does KIP transform document files into structured internal chunks?"*
  - The retrieval result succeeded completely ($Hit@1 = True, Hit@5 = True, RR = 1.000$).
  - The inter-case delay configured in `run_v1_2_expanded_baseline.py` was **0.5 seconds**.
  - `GeminiEmbeddingProvider` relies on `google.genai.Client` without explicit application-level retry loops or custom timeout overrides.
  - The `google-genai` SDK incorporates default exponential backoff retry policies for rate-limit responses (HTTP 429) and transient gateway errors (HTTP 503/504).
  - A 55-second wall-clock delay with eventual full success is the signature behavior of an upstream HTTP 429 rate-limit backoff window executed inside the underlying SDK client.
- **What Remains Unknown:**
  - Because runner logs were not configured with DEBUG-level HTTP trace logging for urllib3/httpx, the exact number of retry cycles and the HTTP status codes returned by Google's endpoints cannot be proven definitively without log artifacts.
  - The proportion of the 55 seconds spent in Gemini embedding versus Qdrant Cloud cannot be distinguished due to monolithic timing.

#### Impact on Evaluation Reporting
Reporting a "mean retrieval latency of 1,261 ms" creates a severely distorted impression of system performance. In 78 of 80 cases, retrieval completed between 500 ms and 735 ms. The adjusted mean latency excluding `exp-018` is **579.5 ms**.

## 7. Evaluation-Integrity Findings

A comprehensive audit of the evaluation suite (`evaluation/models.py`, `evaluation/runner.py`, and dataset schemas) identified several methodological considerations:

1. **Disjunctive Matching in Multi-Document Cases (`runner.py`):**  
   In `EvaluationRunner._evaluate_case()`, Hit Rate and MRR are computed as:
   ```python
   hit = any(d in retrieved_doc_ids for d in case.expected_document_ids)
   ```
   For queries with multiple expected documents (such as the 8 `cross_document` cases), retrieving **at least one** target document satisfies `hit=True` and records Reciprocal Rank based on that first match. In `exp-065`, 2 documents were required; only 1 was retrieved, yet the harness reported `Hit@1 = 1.0` and `MRR = 1.000`. The evaluation harness does not currently compute multi-document Recall@K or Mean Average Precision (MAP).

2. **Ground-Truth Incompleteness & Fact Duplication:**  
   In multiple instances, the expanded corpus contains factual information duplicated across multiple architecture documents. When a query targets that fact, the ground truth only annotated one document:
   - `exp-005`: Annotated `kip_retrieval_and_rag.txt`; `kip_configuration_settings.txt` (retrieved #1) contains the identical setting.
   - `exp-007`: Annotated `kip_llm_gateway.txt`; `kip_retrieval_and_rag.txt` (retrieved #3) answers the question directly.
   - `exp-008`: Annotated `kip_docker_and_deployment.txt`; `kip_api_specifications.txt` (retrieved #1) specifies the exact route.
   - `exp-074`: Annotated `kip_document_parsers.txt`; `kip_security_threat_model.txt` (retrieved #2) and `kip_batch_ingestion_limits.txt` (retrieved #1) specify the DoS size limit.
   - `exp-079`: Annotated `kip_error_handling_protocols.txt`; `kip_security_threat_model.txt` (retrieved #1) contains the verbatim secret sanitization fact.  
   *Impact:* Artificial depression of Hit@1 and MRR on factually successful retrievals.

3. **Absence of Chunk Boundary Failures:**  
   The benchmark category `boundary_handling` was intended to test edge cases. However, because all 50 documents were under 900 characters, each document generated exactly 1 chunk. The suite does not evaluate true chunk-boundary split handling (where a fact crosses a 1,000-character boundary).

4. **Near-Duplicate Queries:**  
   An automated pairwise SequenceMatcher audit across all 80 queries found only one pair with similarity $> 0.65$:
   - `exp-013`: *"How is Qdrant cosine distance converted to a similarity score in KIP?"* (exact_terminology)
   - `exp-038`: *"How does QdrantVectorStoreProvider map cosine distance metrics into similarity scores?"* (multi_concept)  
   All other 78 queries are semantically and lexically distinct.

5. **Lack of Held-Out Evaluation Split:**  
   Currently, all 80 cases serve as a single monolithic benchmark. To prevent data snooping and hyperparameter overfitting during future optimization sweeps, the benchmark should be formally split into a development set (e.g., 50 cases) and a held-out test set (e.g., 30 cases).

## 9. Recommended Next Experiment

### Recommended Direction: Two-Stage Retrieve-and-Rerank with a Cross-Encoder

Based on the evidence that **100% of multi-concept queries succeed** while **68.75% of hard negative queries suffer rank degradation or misses**, the primary bottleneck of KIP retrieval is not dense candidate generation, but **coarse dense ranking precision and susceptibility to topical distractors**.

Dense bi-encoders encode queries and passages independently, leaving the system blind to fine-grained token-level cross-interactions. A cross-encoder reranker processes the query and passage simultaneously through full self-attention layers ($[CLS] \text{ query } [SEP] \text{ passage } [SEP]$), directly evaluating whether the passage affirmatively answers the question.

#### Experiment Specification

1. **Targeted Failure:**  
   `HARD_NEGATIVE_CONFUSION` and `RANKING_ERROR` across the 15 ranking errors and candidate-retrieved hard negatives.

2. **Hypothesis:**  
   Applying a cross-encoder reranker to the top-20 dense retrieval candidates will allow cross-attention to recognize that distractor documents describe non-adopted technologies or tangential proposals, re-ranking the genuine KIP implementation documents to position 1 and improving overall MRR by $\ge 0.08$.

3. **Control:**  
   The unchanged v1.2 expanded baseline:
   - Embedding: `gemini-embedding-2` (768 dimensions)
   - First-stage top-k: 5
   - Reranker: None (pure dense cosine similarity)
   - Corpus: 50 documents (`benchmarks/corpus_v1_2_expanded`)
   - Benchmark: 80 cases (`benchmarks/kip_v1_2_expanded_benchmark.json`)

4. **Treatment:**  
   - First-stage retrieval: Retrieve candidate $top\_k = 20$ from Qdrant using Gemini dense embeddings.
   - Second-stage reranking: Re-score the 20 candidate passages using a lightweight cross-encoder (e.g., `cross-encoder/ms-marco-MiniLM-L-6-v2` locally, or Cohere Rerank API).
   - Final retrieval output: Top 5 reranked chunks.
   - All other parameters (workspace, collection, chunking, corpus, benchmark) remain identical.

5. **Primary Metrics:**  
   - **Hit Rate @ 1** (Baseline: 0.6875)
   - **Mean Reciprocal Rank (MRR)** (Baseline: 0.7623)

6. **Secondary Metrics:**  
   - **Hit Rate @ 5** (Baseline: 0.8750)
   - **Hard Negative MRR** (Baseline: 0.4427)
   - **Reranker Stage Latency (ms)**

7. **Expected Trade-Offs:**  
   - **Latency Overhead:** Cross-encoder inference across 20 passages will add approximately 30–80 ms of local CPU/GPU compute time per query (or 100–200 ms if using an external API).
   - **Dependencies:** Requires adding `sentence-transformers` or an API adapter client.

8. **Measurable Success Criteria:**  
   - Overall **MRR increases from 0.7623 to $\ge 0.8500$** ($+0.0877$).
   - **Hard Negative MRR increases from 0.4427 to $\ge 0.6500$**.
   - **Hit Rate @ 1 increases from 0.6875 to $\ge 0.8000$**.
   - Zero regression on `multi_concept` (must remain $1.000$).

9. **Rejection Criteria:**  
   The experiment must be rejected if:
   - Overall MRR drops below baseline ($< 0.7623$).
   - `multi_concept` Hit@1 regresses below $1.0000$.
   - P95 retrieval latency increases by more than 300 ms over steady-state baseline ($> 950$ ms).

## 10. Limitations and Unresolved Questions

1. **Absence of Numeric Similarity Scores in Baseline Results:**  
   Because `RetrievalMetrics` omitted a numeric score array, exact cosine distance scores between rank 1 and rank 5 were not captured in `kip_v1_2_expanded_baseline_20261014_112147.json`. While rank order and document identities are 100% verified, the numerical similarity margin between target documents and distractors remains unquantified.

2. **Single-Run Observational Nature:**  
   The baseline represents a single run of 80 cases. While deterministic fakes yield identical results, provider-backed embeddings and cloud vector search are subject to minor floating-point variations and network dynamics. Statistical significance testing ($p$-values) will require multi-seed or repeated runs during v1.2 experiments.

3. **Flat Single-Chunk Documents:**  
   Because all 50 corpus files are $< 1,000$ characters, the expanded baseline did not measure chunk boundary behavior under multi-chunk document segmentation. True chunk boundary analysis will require multi-page documents (e.g., 3,000–8,000 characters).

4. **Granular Timing Traces:**  
   Due to monolithic timer wrapping in `runner.py`, the exact division of latency between Gemini embedding generation, Qdrant Cloud network transit, and Qdrant HNSW execution remains unseparated. Stage-level timing instrumentation should be introduced in the evaluation runner for v1.2 experiments.
