## 1. Executive Summary

This experiment tested whether applying Google's recommended asymmetric textual input formatting for `gemini-embedding-2` improves retrieval quality over unformatted raw text, using an isolated controlled comparison against the 18-document v1.2 pilot corpus and 25-case benchmark.

The `task_type` API parameter documented for some Gemini embedding models is **not supported** by `gemini-embedding-2`. The experiment therefore implemented equivalent intent via textual prefix tokens: a task-prefixed query string for retrieval and a title-prefixed chunk string for indexing.

**Paired case-level analysis:** 23 of 25 queries (92%) returned identical rankings. One query improved (rank 2 → rank 1) and one degraded (rank 1 → rank 2). Net MRR delta = **0.0000**.

**Decision:** The formatting treatment is **NEUTRAL**. Raw-text embedding remains the production default, avoiding unnecessary token overhead and API coupling to a specific prefix convention.

## 2. Research Question & Hypothesis

**Research Question:**  
Does applying asymmetric textual input formatting to `gemini-embedding-2` — specifically a task-prefixed query and a title-prefixed document chunk — improve retrieval MRR and Hit Rate compared to unformatted raw text on the KIP v1.2 pilot benchmark?

**Hypothesis:**  
Google's documentation for Gemini embedding models recommends asymmetric formatting to distinguish query-side and document-side embedding spaces. Applying equivalent textual prefixes (`task: question answering | query: {q}` and `title: none | text: {chunk}`) should shift query and document embeddings into better-aligned asymmetric representation spaces, raising MRR above the raw-text baseline.

**Falsification Condition:**  
The hypothesis is falsified if the treatment MRR is equal to or lower than the control MRR across the full 25-case benchmark.

## 3. Technical Background

### 3.1 `task_type` API Constraint

The official Gemini embedding API exposes a `task_type` parameter (e.g., `RETRIEVAL_QUERY`, `RETRIEVAL_DOCUMENT`) for models that support asymmetric fine-tuning. **`gemini-embedding-2` does not support `task_type`** — the parameter is silently ignored or raises a validation error depending on the client version.

This experiment implemented the intent of asymmetric formatting using only textual prefix tokens, which are processed identically by the tokenizer regardless of `task_type` support:

- **Document indexing:** `"title: none | text: {chunk_text}"`
- **Query retrieval:** `"task: question answering | query: {query_text}"`

Both formatters are provider-neutral callables injected via `doc_formatter` in `EmbeddingService` and `query_formatter` in `RetrievalService`, leaving the model API call itself unchanged.

### 3.2 Experiment Scope Limitations

This is a **pilot-scale** experiment. Key scope constraints:

1. **18-document corpus, 25-case benchmark.** The corpus (`benchmarks/corpus_v1_2/`) contains 18 KIP architecture documents covering 11 architectural topics plus 4 distractor topics. Hit Rate@3 and Hit Rate@5 both saturate at **1.0000** for both conditions, meaning the benchmark cannot distinguish improvements beyond rank-3 retrieval. The experiment is only powered to measure rank-1 and rank-2 effects.
2. **No statistical significance testing.** With 25 cases and a single swap at each end (+1/−1), the observed net delta of 0.0000 is consistent with both a true null effect and with measurement noise. No p-value or confidence interval is claimed.
3. **Single run per condition.** Each condition was run once. Embedding API responses are deterministic given identical inputs, but latency measurements carry network variance (~±50 ms).

## 7. Limitations & Scope Qualifications

1. **Benchmark saturation:** Hit Rate@3 and Hit Rate@5 are both 1.0000 for both conditions. This means the benchmark cannot discriminate any improvement at ranks 3–5. A larger, harder benchmark is required to fully assess the formatting effect.
2. **Pilot corpus size:** 18 documents is too small to reveal whether formatting helps on semantically similar or ambiguous queries. The subsequent 50-document / 80-case expanded benchmark was specifically designed to address this.
3. **Single-run measurement:** No repeated sampling was performed. Embedding outputs are deterministic for identical inputs, but ranking ties at fractional cosine scores may be broken differently across runs.
4. **`task_type` not tested:** The `task_type` API parameter, the intended mechanism documented by Google, could not be tested because `gemini-embedding-2` does not support it. The textual prefix approach is an approximation of the intended asymmetric encoding.
5. **No LLM response evaluation:** LLM was disabled for this experiment. Only retrieval metrics (MRR, Hit Rate) were collected. Keyword coverage is 0.0 because no answer was generated.

---

## 8. Engineering Decisions

### Decision 1 — Raw-Text Default Retained

Because the treatment produced exactly neutral retrieval performance (net MRR delta = 0.0000), **raw-text embedding remains the production default** for both `EmbeddingService` (document indexing) and `RetrievalService` (query retrieval). Applying textual prefixes in production would:

- Add latency jitter to every embedding call (prefix tokens processed by tokenizer).
- Couple the system to a specific prefix convention that may need to change if the model changes.
- Provide no measurable retrieval benefit on this corpus.

### Decision 2 — Formatter Extension Hooks Preserved

The provider-neutral `doc_formatter` and `query_formatter` callable parameters added to `EmbeddingService` and `RetrievalService` remain in the codebase with `None` defaults. This allows future experiments (e.g., with a model that genuinely benefits from asymmetric formatting) to inject custom formatters without modifying the service layer.

### Decision 3 — Benchmark Scope Upgrade Required

The saturation of Hit@3 and Hit@5 at 1.0000 on this 18-document pilot confirms that a larger, harder benchmark is necessary. The 50-document / 80-case expanded benchmark (`benchmarks/kip_v1_2_expanded_benchmark.json`) was subsequently constructed specifically to remove saturation and enable discriminative evaluation of hybrid retrieval, cross-encoder reranking, and chunking strategies.
